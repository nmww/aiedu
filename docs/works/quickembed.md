# QuickEmbed · 文本向量化服务

![QuickEmbed 向量化服务](../assets/covers/embedding.jpg)

!!! quote "一句话"
    自建的文本向量化基础设施——两个空间分工：**引擎负责算，网关负责管**。

**访问入口**：
引擎 [modeai-embedding.ms.show](https://modeai-embedding.ms.show) · 网关 [modeai-embedding-gw.ms.show](https://modeai-embedding-gw.ms.show)

**技术栈**：Ollama · `qwen3-embedding:0.6B` · Flask · SQLite

---

## 解决什么问题

做知识库问答（RAG）时，向量化是必经环节。用第三方向量 API 的问题很直接：**数据要出域**，而且按量计费、难以控制成本。

自建服务的好处是：教学资料不出内网，调用次数自己说了算，接口形态还能按自己的需要定制。

---

## 架构：为什么拆成两个空间

```
   调用方（应用 / 老师）
          │
          ▼
┌───────────────────────────┐
│  网关空间 embedding-gw      │  ← 轻量，可频繁部署（约 3 分钟）
│  · 统一入口 /v1/embeddings  │
│  · 鉴权 / 限流 / 黑白名单    │
│  · 用量统计 + 监控大屏       │
└────────────┬──────────────┘
             │ 内部调用
             ▼
┌───────────────────────────┐
│  引擎空间 embedding         │  ← 重，冻结不动（2GB 镜像，重部署约 40 分钟）
│  · Ollama + qwen3-embedding│
│  · 模型权重 + 用量库持久化   │
└───────────────────────────┘
```

这么拆的理由很简单：**引擎镜像大、重部署慢，但很少需要改；网关轻、要经常调策略，但改动风险低。**

合在一起的话，每次调一下限流阈值都要等 40 分钟。拆开之后，改网关 3 分钟上线，引擎完全不受影响——调用方的地址也从来没变过。

## 核心能力

| 能力 | 说明 |
| --- | --- |
| **OpenAI 兼容接口** | `POST /v1/embeddings`，可直接替换现有 OpenAI SDK 调用 |
| **简化接口** | `POST /api/embed`，面向简单场景 |
| **限流保护** | 30 次 / 分钟 / IP；连续违规触发冷却 |
| **黑白名单** | 名单持久化，重启不丢失 |
| **用量统计** | 每次调用入库，配套监控大屏查看调用趋势 |
| **双令牌机制** | 用户调用令牌与管理员令牌分离，监控台不对外暴露 |
| **数据持久化** | 模型权重、Ollama 数据、用量库都在持久化目录，重建不丢 |

## 实测性能

| 场景 | 耗时 |
| --- | --- |
| 单条 · 冷启动 | 约 12.1 s |
| 单条 · 热态 | 约 1.7 s |
| 批量 · 逐条串行 | 约 1.37 s / 段 |
| 网关侧冷调用 | 约 0.84 s（不含引擎冷启） |

**冷启动是这类服务的主要体验瓶颈。** 资源空闲约 10 分钟后模型会被换出，下一次调用需要重新加载。实际使用中如果调用频率稳定，基本都命中热态。

## 集成提示

!!! warning "调用时请携带浏览器 User-Agent"
    平台的网关层对无 `User-Agent` 的请求会直接拒绝。用 `curl` 或后端 HTTP 客户端调用时，记得带上 UA，否则会收到 403——这个现象容易误判成鉴权失败。

## 关于这个项目的价值

它不是一个「用户能看见」的产品，而是**被其他项目依赖的基础组件**。QuickClass 的知识仓库功能、以及后续任何需要语义检索的场景，都可以接到这套服务上。

把基础设施单独做扎实、把接口做稳定，上层应用才能放心地快速迭代。
